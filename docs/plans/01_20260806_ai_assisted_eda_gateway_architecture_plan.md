# 01_20260806 AI 辅助 EDA Gateway 架构与演进计划

## 1. 文档目标

本文定义 `eext-run-api-gateway` 在 AI 辅助分析与绘制原理图、PCB 场景中的职责边界、演进顺序和验收要求。

核心结论：

```text
EasyEDA 内只保留一个通用 Gateway 插件
+
本机 easyeda-api Bridge、分析工具与事务平台
+
原理图、PCB、工程同步等专业 Skill
```

当前不新增第二个 EasyEDA 插件。

## 2. 架构决策

### 2.1 插件定位

`eext-run-api-gateway` 是 EasyEDA 运行时中的轻量执行端，负责：

1. 与本机 Bridge 建立并维持 WebSocket 连接；
2. 读取 EasyEDA 当前运行时上下文；
3. 接收经过 Bridge 校验的命令；
4. 调用 EasyEDA API 执行读取或受控写操作；
5. 监听工程、文档、图元变化事件；
6. 传输结果、错误、进度和工程导出数据；
7. 在 EasyEDA 内显示必要的确认、警告和结果通知；
8. 写操作后执行保存、回读与结果回传。

### 2.2 插件不承担的职责

以下内容不得逐步堆入插件：

1. 电路功能设计与需求推理；
2. 器件选型和数据手册结论；
3. 原理图模块划分与布局算法；
4. PCB 功能分区、布线策略和回流路径分析；
5. 大规模几何计算、图算法和语义差异分析；
6. `.eprj3`、`.epro2` 的长期存储、历史版本和 Git 管理；
7. AI 工作流、提示规则和专业设计规范；
8. 未经确认的自动双向覆盖或无人值守写入。

这些职责分别属于 `easyeda-api` 本机平台和专业 Skill。

## 4. 为什么当前不新增第二个插件

### 4.1 一个插件已经能够覆盖运行时能力

现有 Gateway 已具备 EasyEDA 内部 API 调用、WebSocket 通信和菜单入口基础。后续的变化监听、二进制传输和受控执行均属于同一运行时网关职责，不需要新建独立扩展。

### 4.2 避免多个插件争用同一文档

两个插件同时持有连接、监听事件或执行写操作，容易造成：

1. 重复事件；
2. 重复导出；
3. 写事务相互覆盖；
4. 连接和窗口标识不一致；
5. 无法统一确认、回滚和审计；
6. 用户难以判断应安装、启用哪个插件。

### 4.3 设计规则应快速迭代

原理图和 PCB 规则变化频繁，应由 Skill 和本机工具更新，而不是每次修改规则都重新编译、打包和安装 EasyEDA 插件。

## 5. 未来重新评估拆分插件的条件

只有满足以下至少一个明确条件时，才评估第二个插件：

1. EasyEDA 权限模型要求把只读连接和高权限写操作分开授权；
2. 需要独立发布一个面向普通用户的重型可视化交互面板；
3. Marketplace 审核或发行策略要求读写能力分别发布；
4. Gateway 单包体积、启动时间或运行内存因 UI 功能显著失控；
5. 不同团队需要独立版本周期，且无法通过协议版本兼容解决；
6. EasyEDA 运行时限制导致一个扩展无法同时安全处理连接、事件和受控写入。

未出现以上事实前，不以“功能较多”为理由拆分插件。

## 6. 插件内部逻辑分层

受当前仓库单入口约束，第一阶段仍保留 `src/index.ts` 单入口，但代码逻辑应按以下区域组织，避免业务混杂：

1. `ConnectionManager`
   - 自动连接开关；
   - 端口扫描；
   - 握手验证；
   - 心跳；
   - 断线重连；
   - 手动停止与自动停用区分。

2. `EasyEdaEventObserver`
   - 原理图图元变化；
   - PCB 图元变化；
   - 页面或文档切换；
   - 保存状态变化；
   - 防抖和事件合并；
   - 仅上报事实，不在插件内做设计判断。

3. `ToolExecutionDispatcher`
   - 协议版本检查；
   - 请求 ID；
   - 目标窗口和文档校验；
   - 超时状态回传；
   - 只允许白名单命令或受控计划；
   - 保留兼容执行入口但不得绕过写保护。

4. `BinaryTransferAdapter`
   - 工程、文档和快照的分块传输；
   - 分块序号、长度、哈希和确认；
   - 中断后明确失败，不把不完整文件标记为成功；
   - 大文件不长期使用单个 Base64 JSON 消息。

5. `WriteTransactionExecutor`
   - 事务 ID；
   - 工程、文档、页面和基线哈希校验；
   - 执行最小操作集合；
   - 收集实际生成的 Primitive ID；
   - 保存与回读；
   - 返回部分成功和失败阶段；
   - 不在插件内决定布局方案。

6. `NotificationAdapter`
   - 连接状态变化通知；
   - 在线工程已导出通知；
   - 本地工程有更新通知；
   - 写操作确认；
   - 冲突、回读失败和未知结果警告；
   - 限流，避免 Toast 刷屏。

## 7. 重连改进计划

当前有限次数重试会导致 Bridge 晚启动后插件永久停止发现。改为显式状态机：

```text
DISABLED
MANUAL_STOPPED
SCANNING
CONNECTING
CONNECTED
BACKOFF
WAITING_BRIDGE
ERROR
```

规则：

1. 自动连接启用时不得因达到固定次数而永久停止；
2. 使用带抖动的封顶指数退避，例如 1、2、4、8、15、30 秒；
3. 用户手动停止后不得被后台重试立即重新连接；
4. 自动连接开关变化必须立即生效；
5. 同一 WebSocket ID 重注册前必须先关闭旧连接；
6. Toast 只在状态发生有意义变化时显示；
7. 心跳失败后先清理旧状态，再进入退避扫描；
8. 重连后重新获取窗口会话标识，旧 `windowId` 不得继续使用。

## 8. 在线工程变化与导出

插件只负责感知变化和调用 EasyEDA 导出 API，不负责本地历史管理。

建议流程：

```text
EasyEDA 图元变化
→ 标记 dirty
→ 事件防抖
→ 请求 easyeda-api 决定是否导出
→ 插件导出当前文档或完整工程
→ 分块发送
→ easyeda-api 原子保存并校验
→ 插件显示同步结果
```

第一阶段策略：

1. 在线到本地允许自动更新；
2. 本地到在线只通知，不自动覆盖；
3. 在线和本地同时变化时进入冲突状态；
4. 插件不得自行决定冲突覆盖方向；
5. 导出失败不得删除或覆盖上一份有效本地文件。

## 9. 受控写操作安全边界

写操作按照能力逐级开放：

### 9.1 Level 0：只读

读取上下文、器件、导线、网络、PCB 图元、BBox 和工程文件。

### 9.2 Level 1：单对象最小修改

创建、移动或旋转一个原理图器件；创建一条短导线；创建一个网络标记。必须保存、回读和验证。

### 9.3 Level 2：小批量事务

基于已确认计划执行一组互相关联的操作，并记录全部创建或修改的 Primitive ID。

### 9.4 Level 3：原理图生成事务

从已解析和预览的网表或设计计划生成测试图页，支持事务级验证和本次创建对象回滚。

### 9.5 Level 4：PCB 修改

PCB 器件移动、旋转和受控走线应晚于原理图写能力，且必须增加板框、禁布区、网络、电气约束和 DRC 前后验证。

任何等级都不得默认开启无人值守自动写入。

## 10. 协议演进建议

在现有消息基础上逐步增加：

```text
state.changed
eda.event
file.begin
file.chunk
file.ack
file.end
transaction.prepare
transaction.confirm
transaction.execute
transaction.progress
transaction.result
transaction.verify
transaction.rollback
```

每条消息至少包含：

```text
protocolVersion
requestId 或 transactionId
windowId
timestamp
payload
```

写事务还必须包含：

```text
projectIdentity
documentIdentity
pageIdentity
baselineHash
operationCount
requiresConfirmation
```

## 11. 工作包

### WP-G1：重连可靠性

1. 实现连接状态机；
2. 无限封顶退避；
3. 自动连接开关即时生效；
4. 清理重复 Toast；
5. 验证 Bridge 先启动、后启动、重启和端口变化场景。

### WP-G2：事件观察

1. 接入原理图变化事件；
2. 接入 PCB 变化事件；
3. 实现防抖、合并和事件限流；
4. 明确 Beta API 和实机验证边界。

### WP-G3：工程导出与分块传输

1. 当前文档导出；
2. 完整工程导出；
3. 分块发送和 ACK；
4. 长度、SHA-256 和最终状态验证；
5. 断线和超时测试。

### WP-G4：确认和通知

1. 在线工程同步成功；
2. 本地工程更新提醒；
3. 冲突提醒；
4. 写操作确认；
5. 通知限流和多语言。

### WP-G5：受控写执行器

1. 先实现单对象事务；
2. 再实现小批量事务；
3. 保存与回读；
4. 部分失败报告；
5. 本次事务创建对象回滚。

## 12. 测试与验收

仓库当前没有自动化测试框架，代码修改至少执行：

```bash
npm run lint
npm run build
```

涉及 EasyEDA 运行时的改动还必须进行实机验证。

### 12.1 重连验收

1. Bridge 先启动，插件成功连接；
2. 插件先启动，Bridge 30 分钟后启动仍能连接；
3. Bridge 重启后自动恢复；
4. Bridge 端口变化后重新扫描；
5. 手动停止后不自动重连；
6. 重新启用自动连接后立即扫描；
7. 不产生多个活动连接；
8. Toast 不持续刷屏。

### 12.2 事件与导出验收

1. 连续修改被防抖合并；
2. 原理图和 PCB 事件能够区分；
3. 导出期间继续修改时结果状态明确；
4. 大文件分块完整；
5. 断线文件不被标记成功；
6. 完成后本机哈希与发送端一致。

### 12.3 写事务验收

1. 目标工程、文档或页面不匹配时拒绝；
2. 基线哈希变化时拒绝；
3. 用户取消时不产生修改；
4. 超时返回未知结果并要求回读，不直接重试；
5. 部分失败能够列出已完成操作；
6. 保存失败不声称完成；
7. 回读结果与计划一致后才标记成功。

## 13. 非目标

本计划不包含：

1. 在插件中实现 AI 模型；
2. 在插件中硬编码原理图或 PCB 设计规则；
3. 自动生成完整 PCB 走线；
4. 自动覆盖存在冲突的在线工程；
5. 直接合并 `eext-generate-schematic-from-netlist` 的全部代码；
6. 当前阶段新增第二个 EasyEDA 插件。

## 14. 最终结论

`eext-run-api-gateway` 应继续作为唯一 EasyEDA 端插件，并保持“连接、事件、传输、执行、确认、回传”的薄层定位。

AI 对原理图和 PCB 的理解、分析、设计规划、几何计算和安全规则由 `easyeda-api` 与专业 Skill 承担。该分层能够减少插件重装频率、避免多扩展争用文档，并为后续受控写操作提供统一事务边界。
